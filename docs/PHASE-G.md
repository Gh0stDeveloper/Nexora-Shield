# Phase G — VM Shield

## Objective

Phase G adds selective virtualization for high-value methods. The objective is not to translate every DEX method. A method is accepted only when the current VM contract can preserve its supported semantics.

The design is fail-safe: unsupported or ambiguous constructs remain in the ordinary DEX pipeline rather than being force-lowered into an incorrect VM program.

## G.1 — Eligibility analyzer

`EligibilityAnalyzer` evaluates each method before lowering.

It records:

- register count;
- executable instruction count;
- call usage;
- field usage;
- exception regions;
- unsupported opcodes;
- malformed DEX IR.

Policy limits can independently disable calls, fields or exceptions and cap method size/register count.

## G.2 — VM IR

`VmMethod` is a typed intermediate representation containing:

- explicit virtual registers;
- parameter-register mapping;
- instructions;
- constant pool;
- exception handlers.

Every method is validated before execution.

## G.3 — Opcode model

`SemanticOpcode` separates operation meaning from encoded opcode values.

The semantic instruction set currently contains arithmetic, branches, field access, calls, exceptions and return operations required by the supported lowering contract.

`OpcodeStream` serializes the complete VM program, not only opcode identities. Register operands, constant indices, branch targets, field/method ids and call arguments are encoded in a deterministic little-endian format. Decoding requires the per-build opcode allocation.

## G.4 — Lowering

`DexLowerer` lowers only eligible DEX methods.

The initial supported DEX subset includes:

- integer/object moves;
- 32-bit integer constants;
- string/type constants;
- integer add/sub/mul/div/rem/and/or/xor;
- integer negation;
- goto and integer conditional branches;
- instance/static field accesses through the host boundary;
- invoke forms with supported move-result handling;
- explicit throw;
- typed and catch-all exception tables;
- return and return-void.

Unsupported instructions cause explicit rejection. They are not approximated.

## G.5 — Interpreter

`Interpreter` executes validated VM IR with:

- deterministic register state;
- explicit argument mapping;
- wrapping 32-bit integer arithmetic compatible with supported Dalvik int operations;
- configurable step limit;
- deterministic return values;
- execution directly from allocated `OpcodeStream` bytecode;
- no unsafe code.

## G.6 — Exception semantics

The VM represents exception type and value separately.

It supports:

- arithmetic exceptions generated by divide/rem by zero;
- explicit throw;
- host-produced exceptions;
- typed handlers;
- catch-all handlers;
- move-exception register transfer;
- host-provided exception construction;
- host-provided subtype/assignability matching for Java-style catch semantics.

Unhandled exceptions are surfaced explicitly.

## G.7 — Calls and fields

Calls and field operations cross a narrow `VmHost` interface.

The VM never assumes Java object layout. The Android/runtime integration layer is responsible for implementing:

- instance/static field read;
- instance/static field write;
- method dispatch;
- reference exception typing.

This keeps the VM core portable and testable.

## G.8 — Constant pools

`ConstantPool` deduplicates:

- 32-bit integer constants;
- strings;
- type descriptors.

The pool has a deterministic digest used by sealed metadata.

## G.9 — Per-build opcode allocation

`OpcodeAllocation` derives a deterministic private opcode mapping from:

- build id;
- private seed;
- versioned domain separation.

Different build ids produce different opcode maps while preserving semantic opcode sequences.

The private seed is not stored in the opcode map.

## G.10 — Metadata sealing

`MetadataSealer` authenticates VM metadata with HMAC-SHA-256.

Sealed metadata binds:

- method id;
- register count;
- instruction count;
- exception-handler count;
- constant-pool digest;
- opcode-map fingerprint;
- encoded VM bytecode digest.

`verify_program` rejects both a mismatched opcode allocation and any change to the encoded bytecode stream. `verify_executable` additionally authenticates parameter-register mapping and exception-handler metadata before execution.

The protected runtime path is represented by `SealedExecution`. Its debug representation explicitly redacts the seal key.

This is authenticity/integrity protection, not an encryption claim.

## G.11 — Performance estimator

`PerformanceEstimator` provides a deterministic static cost model.

Host-boundary operations and division/rem receive higher weights than simple register/arithmetic operations. The result is suitable for build-time budgets and method-selection decisions.

It is an estimator, not a replacement for device benchmarks.

## G.12 — Differential tests

The test suite compares **encoded VM bytecode execution** against reference semantics across:

- integer boundaries;
- wrapping addition;
- thousands of deterministic generated inputs;
- conditional branch behavior;
- arithmetic-exception behavior.

The phase exit criterion requires these tests to remain green. Differential tests execute through the sealed bytecode path rather than bypassing it with direct IR execution.

## G.13 — Selective annotations/config

`SelectionPlanner` supports four modes:

- config only;
- annotation only;
- config OR annotation;
- config AND annotation.

Configuration selectors use class/method glob patterns. Annotation-based selection accepts method ids produced by the annotation-discovery stage and preserves the configured marker descriptor.

Selection is separate from eligibility: being selected does not guarantee virtualization.

## G.14 — VM security benchmark

`VmSecurityBenchmark` generates multiple per-build opcode allocations and measures:

- unique opcode-map fingerprints;
- maximum shared semantic-to-byte assignments;
- maximum transfer ratio in basis points.

This is a structural diversity regression gate. It does not claim that VM bytecode is cryptographically opaque or impossible to reverse engineer.

## Security boundary

VM Shield increases the work required to recover selected logic. It is one defense layer and assumes the attacker can eventually observe code and runtime behavior on a controlled device.

The design intentionally avoids:

- destructive anti-analysis behavior;
- hidden persistence;
- exploiting the device;
- virtualizing unsupported DEX constructs with guessed semantics.

## Closure requirement

Phase G is complete only when:

1. G.1–G.14 implementation is integrated;
2. VM tests and strict Clippy pass;
3. Rust 1.81 MSRV passes;
4. differential tests pass;
5. security benchmark passes;
6. workspace regressions A–F remain green;
7. documentation and configuration schema match the runtime contract.
